# LAPAS: Research Findings, Methodology and Lessons Learnt

**Project:** LAPAS (Loan Approval Prediction & Advisory System), Honours project, University of Johannesburg
**Covers:** development from July 2026 to the optimisation pass of 20 September 2026
**Compiled:** 26 September 2026
**Purpose:** source material for the final research document. It records what was built, how it was measured, what worked, what broke, what was changed and why, and what was learnt. Every number here comes from a file in this repository; the source file is named next to each table so it can be re-checked or regenerated.

> Style note: this file uses no em dashes, matching the rule in the advisor's system prompt and the paper's formatting constraints.

---

## 1. Summary

LAPAS has three connected pipelines, served through a FastAPI backend, a PostgreSQL database and a five-page Streamlit frontend:

1. **Loan approval prediction:** four classifiers compared on a 45,000-row applicant dataset.
2. **RAG advisory generation:** per-applicant advisory reports grounded in real regulatory and lending-policy documents, generated by Mistral-7B-Instruct.
3. **Retrieval benchmark:** a controlled comparison of sparse (TF-IDF) and dense (sentence-embedding) retrieval for the RAG step.

**Headline outcomes**

| Area | Result |
|---|---|
| Best classifier | **XGBoost (tuned)**: ROC-AUC **0.9784**, accuracy 0.9359, MCC 0.8099, Brier 0.0465 |
| Model selection | XGBoost now wins **both** the single-metric (ROC-AUC) selection and the composite multi-metric rank. Before tuning, these two methods disagreed. |
| Retrieval quality | Dense retrieval scores well above TF-IDF on relevance (top-1 0.635 vs 0.248) |
| Retrieval cost | Dense retrieval is **~5.7x slower** than TF-IDF (23.3 ms vs 4.1 ms mean) |
| Retriever agreement | Jaccard overlap 0.433, Spearman rho 0.633: the two methods partly agree but cannot be swapped for each other |
| Biggest RAG fix | A silent truncation bug meant the embedding model never saw the second half of every chunk. Fixing it improved every retrieval metric. |
| Biggest ML fix | An sklearn class-inheritance bug made logistic-regression tuning produce `nan` scores. Once fixed, tuning worked for all four models. |
| Human evaluation (Exp. 3) | The database schema for it exists, but **no evaluator data has been collected**. No Kappa value can be reported. |

## 2. Methodology

### 2.1 Dataset

- Source: `data/raw/loan_data.csv` (Kaggle "Loan Approval Classification Data").
- **45,000 rows, 14 raw columns.** Target `loan_status` (1 = approved, 0 = rejected).
- **Class balance: 10,000 approved (22.2%) vs 35,000 rejected (77.8%).** Because the classes are imbalanced, accuracy alone is misleading, so the evaluation uses eight metrics (Section 2.4).
- Cleaning: enum normalisation (e.g. `Doctorate` to `Doctor`, `HOMEIMPROVEMENT` to `HOME_IMPROVEMENT`), the previous-default flag coerced to a boolean, and ages above 100 capped at 100.
- **Currency rescale (modification, Aug 2026):** the dataset is in USD, but the app had been showing those raw figures with an "R" label, so it was displaying dollars as Rand. `database/feature_eng.py` now multiplies `person_income` and `loan_amnt` by `ZAR_INCOME_LOAN_SCALE = 200,000 / 67,048 ≈ 2.9829`. This maps the dataset's median income ($67,048) to a representative South African formal-sector median (R200,000). Both columns get the same factor, so the loan-to-income ratios the model learns from do not change. Income-bucket thresholds were rescaled to match.

### 2.2 Feature engineering (`database/feature_eng.py`)

The 14 raw columns expand to 36: 14 raw or passthrough, 21 engineered, and 1 pipeline-version column. The engineered features fall into these groups:

- **Financial ratios:** `monthly_income`, `debt_to_income_ratio`, `loan_to_income_ratio` (both of these are equal to `loan_percent_income` by construction), `monthly_loan_burden`, `affordability_ratio`, `credit_history_to_age_ratio`.
- **Age/employment:** `emp_to_age_ratio`, `loan_per_age`, `young_inexperienced`, `employment_stability`.
- **Credit quality:** `credit_score_tier` (FICO-style bands), `thin_credit_file` (history under 2 years), `score_per_history_year`, `credit_risk_interaction`.
- **Risk:** `composite_risk_score`, a weighted sum of seven binary risk signals with weights summing to 1.0: DTI > 0.40 (0.20), LTI > 0.40 (0.15), thin file (0.10), credit-risk interaction (0.15), high loan burden (0.10), previous default (0.20), young and inexperienced (0.10). `is_high_risk` flags scores at or above the 75th percentile.
- **Ordinal encodings:** `homeownership_score` (0 to 3), `intent_risk_score` (0 = EDUCATION to 5 = VENTURE), `stability_income_interaction`.

**Design detail that affects reproducibility:** `credit_risk_interaction` and `is_high_risk` depend on dataset-wide medians and quantiles. A single new applicant cannot produce those statistics, so the backend's single-row path (`backend/services/feature_engineering.py`) reuses precomputed reference statistics from `backend/services/reference_stats.py`.

### 2.3 Classifiers (`src/classifier/`)

A common `LoanClassifier` wrapper exposes the same API for every algorithm (`train / predict / predict_proba / tune / save / load`), each built as a scikit-learn `Pipeline`:

| Model | Imbalance handling | Scaling |
|---|---|---|
| Random Forest | `class_weight="balanced"` | none (tree splits are scale-invariant) |
| XGBoost | `scale_pos_weight = n_neg / n_pos`, computed at fit time | none |
| Gaussian Naive Bayes | n/a | `StandardScaler` |
| Custom Logistic Regression (from scratch: mini-batch SGD with Adam, L1/L2/elastic-net) | `class_weight="balanced"` | `StandardScaler` |

- Split: stratified, `test_size=0.2`, `random_state=42`.
- **Hyperparameter search:** `RandomizedSearchCV` / `GridSearchCV` over `StratifiedKFold` (5 folds), scored on `roc_auc`. Run with `scripts.train_model --tune --tune-n-iter 30`.
- **Tuned champion hyperparameters** (from `models/best_model.json`): XGBoost with `n_estimators=100, max_depth=9, learning_rate=0.2, subsample=0.9, colsample_bytree=0.9, reg_alpha=0.1, reg_lambda=5.0, min_child_weight=5`.

### 2.4 Evaluation (`src/classifier/evaluate.py`)

- Eight metrics: accuracy, precision, recall, F1 (macro), F1 (weighted), ROC-AUC, average precision, Brier score, MCC.
- **Composite rank:** each model is ranked on ROC-AUC, F1-weighted, average precision, accuracy and MCC (higher is better) and on Brier (lower is better). The composite is the mean of those six ranks.
- **Champion selection:** a single configurable metric (`MODEL_SELECTION_METRIC`, default ROC-AUC) chooses the model saved to `models/best_model.joblib`.

### 2.5 RAG advisory pipeline (`src/ai_advisor/`)

1. **Corpus:** 8 documents in `data/loan_strategy_docs/`. Four are PDFs: Basel credit-risk principles, the CFPB credit-score guide, the NCR debt-management guide and the NCR National Credit Act consumer guide. Four are plain-text policy files: credit guidelines, improvement roadmap, lending policy and risk assessment. *(An earlier brief listed 9 documents including a World Bank report. That file is not in the corpus, so the paper should say 8.)*
2. **Chunking:** overlapping word windows, **180 words with a 30-word overlap** (changed from 400/50, see Section 4.1).
3. **Two interchangeable indexes over the same chunks:**
   - Sparse: `TFIDFStore` (sklearn `TfidfVectorizer`, unigrams and bigrams, sublinear TF, 20k vocabulary, English stop words removed, cosine similarity).
   - Dense: ChromaDB `PersistentClient` with `all-MiniLM-L6-v2` embeddings and an HNSW cosine index. Embeddings are computed explicitly and passed to Chroma.
4. **Context building:** `LoanContextBuilder` rebuilds the training-time feature vector (one-hot columns aligned to the model's feature list), scores it with the champion model, and packages the prediction, risk tier and top-15 global feature importances.
5. **Generation:** `LoanAdvisor.advise()` retrieves the top 5 chunks and calls `mistralai/Mistral-7B-Instruct-v0.2` through `InferenceClient.chat_completion()` with system and user messages, `temperature=0.4` and `max_tokens=1500`. If the LLM is unavailable, a deterministic rule-based Markdown report is produced instead.
6. **Local explainability:** `backend/services/lime_service.py` runs LIME (15 features, 5,000 perturbation samples) for each applicant. The project uses LIME, not SHAP, to avoid a `numba`/`llvmlite` dependency conflict on macOS Intel.
7. **Default retriever in the live system:** the `/advisory` endpoint defaults to `retriever="tfidf"`, with `"vector"` available on request.

### 2.6 Retrieval benchmark (`scripts/tfidf_chroma.py`)

- 20 hand-written, domain-specific queries (e.g. "applicant with poor credit score and high debt to income ratio"), each run against both stores over the same chunked corpus.
- Metrics per query: latency (ms), top-1 similarity, mean similarity, Jaccard overlap of the two result sets, and Spearman rank correlation where it is defined.
- Outputs: `reports/tfidf_chroma_metrics.csv` plus 5 charts. The paper figures are regenerated separately into `figs/` by `scripts/generate_paper_figures.py`, using a warm, neutral palette with no blue.

## 3. Results

### 3.1 Experiment 1: Classifier comparison

Source: `models/model_comparison.csv` (after tuning). The "Before" figures are the untuned run recorded in the previous research brief.

| Rank | Model | Accuracy | Precision | Recall | F1 (w) | ROC-AUC | Avg Prec | Brier ↓ | MCC |
|---|---|---|---|---|---|---|---|---|---|
| 1 | **XGBoost** (champion) | 0.9359 | 0.8903 | 0.8115 | 0.9348 | **0.9784** | 0.9403 | **0.0465** | **0.8099** |
| 2 | Random Forest | 0.9309 | 0.8497 | 0.8370 | 0.9307 | 0.9765 | 0.9345 | 0.0510 | 0.7990 |
| 3 | Logistic Regression (custom) | 0.8376 | 0.5841 | 0.9340 | 0.8487 | 0.9517 | 0.8474 | 0.1004 | 0.6463 |
| 4 | Gaussian Naive Bayes | 0.7846 | 0.5080 | 0.9640 | 0.8021 | 0.9343 | 0.7874 | 0.1973 | 0.5870 |

**Before vs after tuning**

| Model | Metric | Untuned | Tuned | Change |
|---|---|---|---|---|
| XGBoost | Accuracy | 0.9193 | 0.9359 | +1.7 pts |
| | MCC | 0.7821 | 0.8099 | +2.8 pts |
| | Brier ↓ | 0.0555 | 0.0465 | -16% |
| Random Forest | MCC | 0.7872 | 0.7990 | +1.2 pts |
| Logistic Regression | ROC-AUC | 0.9269 | 0.9517 | +2.5 pts |
| | MCC | 0.6083 | 0.6463 | +3.8 pts |
| | Brier ↓ | 0.1498 | 0.1004 | -33% |
| Naive Bayes | Accuracy | 0.7632 | 0.7846 | +2.1 pts |

**Interpretation**

- The two tree ensembles beat the linear and probabilistic baselines on almost every metric: ROC-AUC above 0.976, against 0.95 and 0.93 for the other two.
- **Model-selection disagreement resolved.** Untuned, Random Forest won the composite rank (1.33) while XGBoost won on ROC-AUC alone (0.9776 vs 0.9757), so the two selection methods picked different models. After tuning, XGBoost has the best composite rank (1.0) and also the best Brier score, so both methods agree. This is worth reporting: the earlier disagreement came from untuned hyperparameters, not from something fundamental.
- Naive Bayes shows the typical pattern of high recall (0.964) with low precision (0.508). Its conditional-independence assumption does not hold here because several engineered features are correlated by design (DTI and LTI are identical). It has only one tunable parameter (`var_smoothing`), so its small gain from tuning is expected.
- The from-scratch logistic regression reaches ROC-AUC 0.95. That is close to library-grade performance, which supports the correctness of the implementation. It gained the most from tuning, but only after the bug in Section 4.2 was fixed.

### 3.2 Experiment 2: Sparse vs dense retrieval

Source: `reports/tfidf_chroma_metrics.csv` (20 queries). The "Before" column is the old 400/50 chunking and "After" is the current 180/30.

| Metric | Before | After | Change |
|---|---|---|---|
| TF-IDF mean latency | 2.52 ms | 4.09 ms | +1.57 ms (more, smaller chunks) |
| Dense mean latency | 32.45 ms | 23.31 ms | **-28%** |
| TF-IDF top-1 score | 0.192 | 0.248 | **+29%** |
| TF-IDF mean score | 0.133 | 0.168 | +26% |
| Dense top-1 score | 0.598 | 0.635 | +6% |
| Dense mean score | 0.504 | 0.558 | +11% |
| Jaccard overlap | 0.357 | 0.433 | **+21%** |
| Spearman rho | 0.465 | 0.633 | **+36%** |

*Spearman rho is defined for 18 of the 20 queries. Two queries ("steps to improve credit score before reapplying", "how long to wait before reapplying after rejection") have too little overlap between the two result sets to compute it. Both are paraphrased, advice-style queries, exactly where lexical and semantic retrieval diverge most.*

**Interpretation**

- **Dense retrieval returns much higher similarity scores.** Dense top-1 beats TF-IDF top-1 on all 20 queries. This fits dense embeddings matching paraphrases that TF-IDF misses because it only matches shared words. Note that cosine scores from different representations are not directly comparable in absolute terms; the consistent direction across all 20 queries is the stronger evidence.
- **The speed gap narrowed from ~12x to ~5.7x** after the chunking change, but dense retrieval still costs a neural forward pass per query.
- **Agreement is moderate.** A Jaccard overlap of 0.43 means the two methods often return different passages. Some queries even have negative rank correlation (e.g. "venture loan speculative purpose highest risk", rho = -1.0).
- **Part of the earlier disagreement was an artefact.** Both agreement metrics rose sharply once the truncation bug was fixed. The dense side had been working from truncated chunks, so part of the "sparse vs dense" disagreement measured before the fix was actually caused by the bug.
- **Scope:** n = 20 queries over 8 documents. Treat the results as a controlled pilot, not a general claim about sparse vs dense retrieval.

### 3.3 Experiment 3: Human evaluation of advisory quality (not executed)

The `evaluator_assessments` table is built for a three-evaluator panel. Each evaluator would rate each report on four dimensions (policy traceability, factual accuracy, completeness, actionability) on a 1 to 5 Likert scale, comparing RAG-grounded output against a LIME-only baseline, with Cohen's Kappa for inter-rater agreement. **No evaluator data has been collected, so no Kappa value exists.** The paper should present this as designed infrastructure and future work.

## 4. Failures, bugs found, and how each was resolved

These are the most useful material for a "lessons learnt" section, because each one was a silent or non-obvious failure.

### 4.1 Silent embedding truncation (RAG quality bug)

- **Symptom:** none visible. Retrieval "worked" but scored lower than it should have.
- **Cause:** `all-MiniLM-L6-v2` truncates input at 256 tokens. Chunks were ~400 words (~500 to 550 tokens), so **roughly the back half of every chunk was dropped before embedding**, without any warning.
- **Fix:** default chunking changed to 180 words with a 30-word overlap (~230 to 250 tokens) in `document_loader.py`, `vector_store.py` and `tf_idf_store.py`. Both indexes were rebuilt and the benchmark re-run.
- **Effect:** every quality metric improved (Section 3.2), and dense latency fell 28%.
- **Lesson:** chunk size must be chosen against the embedding model's token limit, not picked as a round number. A retrieval pipeline can be wrong without ever raising an error.

### 4.2 sklearn tag-resolution bug in the custom logistic regression

- **Symptom:** tuning logistic regression gave accuracy 0.569 (down from 0.836 untuned). Every cross-validation fold's `roc_auc` came back `nan`, and the "best" parameters were effectively arbitrary.
- **Cause:** the class was declared `CustomLogisticRegression(BaseEstimator, ClassifierMixin)`. In scikit-learn 1.6+, `__sklearn_tags__()` is resolved in class-inheritance order (the MRO). With `BaseEstimator` listed first, it overrode the tags `ClassifierMixin` contributes, which left `estimator_type=None`. `is_classifier()` therefore returned `False`, and every scorer that goes through `decision_function` (including `roc_auc`) failed quietly.
- **Fix:** reorder the bases to `(ClassifierMixin, BaseEstimator)`. After the change, `is_classifier()` returns `True`.
- **Lesson:** a custom estimator can pass basic fit/predict tests and still break sklearn's meta-tools. A library upgrade changed the behaviour without any change to project code.

### 4.3 HuggingFace inference API rejected the prompt format

- **Symptom:** advisory generation failed with "not supported for task text-generation".
- **Cause:** the code built a raw Mistral `<s>[INST]...[/INST]` string and called `text_generation()`. HF inference providers now serve instruct models only through the conversational (chat) task.
- **Fix (Aug 2026):** migrated to `chat_completion()` with system and user messages and added retry logging. The rule-based fallback report was upgraded to three prose paragraphs plus a risk table, so a degraded response is still useful.
- **Lesson:** relying on a hosted third-party model is a single point of failure, and the provider's API can change underneath the project. The fallback path is a necessary part of the design.

### 4.4 USD figures shown as Rand

- **Cause:** the dataset was never converted to Rand; USD amounts were simply displayed with an "R" label.
- **Fix:** a proportional rescale to a South African median income (Section 2.1), followed by retraining, a database reset and repopulation, and clearing the stale Chroma index. The policy documents and frontend help text were updated to the new ranges.
- **Lesson:** localisation is a data-validity problem, not just a label. The rescale keeps the ratios the model learns from, but the absolute thresholds in the policy text had to change with it.

### 4.5 ChromaDB `embedding_function` in a rarely used code path

- The constructor already followed the "no `embedding_function=`" rule, but `from_directory(force_reindex=True)` still passed one. This path would have raised `ValueError` the first time anyone used it. It was removed.
- **Lesson:** code paths that rarely run need the same review as the main path.

### 4.6 Development environment corruption (recurring)

- During the September pass, the `.venv` had compiled extension files missing for numpy, pandas, scipy, pydantic-core, tokenizers, ChromaDB's Rust bindings, scikit-learn and plotly, which crashed imports. It was repaired with `pip install --force-reinstall -e .` (keeping the `torch<2.5` pin).
- **Still open:** as of 26 September 2026, `.venv/bin/python -c "import pandas"` fails again with a numpy import error. The environment needs another force-reinstall before any results are regenerated.
- **Lesson:** on an unsupported platform (macOS Intel, where newer wheels no longer exist), the environment itself is fragile. Pinned dependencies and a documented rebuild procedure matter for reproducibility.

### 4.7 Smaller issues found

- `python database/feature_eng.py` fails with `ModuleNotFoundError: config`. It must be run as `python -m database.feature_eng` so the project root is on `sys.path`.
- Streamlit pages could not import `config`/`src`/`backend`. Each page now adds both `frontend/` and the project root to `sys.path`.
- `AVAILABLE_CLASSIFIERS` listed eight algorithms but only four existed. It was trimmed to the four real ones (SVM, gradient boosting, LightGBM and CatBoost were never implemented).
- **Still inconsistent:** `RAG_CONFIG` in `config/settings.py` still says `chunk_size: 512` and `embedding_model: "text-embedding-3-large"`, neither of which the loader actually uses. The paper should quote 180/30 and `all-MiniLM-L6-v2`.

## 5. Engineering constraints discovered (macOS Intel x86_64)

A large share of the effort went into getting scikit-learn, XGBoost, PyTorch, sentence-transformers and ChromaDB to run together reliably in one process. Documenting how this was done is itself a contribution to reproducibility.

| Constraint | Cause | Symptom | Resolution |
|---|---|---|---|
| Encode texts one at a time | OpenMP/libdispatch thread contention in the Rust tokenizer | SIGSEGV on batch `encode()` | Loop over texts one by one (slower, but stable) |
| Load XGBoost before PyTorch | Two competing OpenMP runtimes | SIGSEGV during `joblib.load()` | Backend warms up the classifier at startup; `VectorStore` is imported lazily; `src/ai_advisor/__init__.py` has no re-exports |
| `OMP_NUM_THREADS=1`, `TOKENIZERS_PARALLELISM=false` | Same OpenMP contention | First dense query hangs indefinitely | Set at the top of `config/settings.py`, before any other import |
| No `embedding_function=` in Chroma | ChromaDB 1.x validates callable signatures strictly | `ValueError` | Embeddings computed and passed explicitly |
| `torch<2.5`, `transformers<5`, `sentence-transformers<4` | No newer macOS x86_64 wheels | Install failure | Pinned in `pyproject.toml` |
| LIME instead of SHAP | `numba`/`llvmlite` conflict | Install/import failure | LIME used throughout |
| `.venv/bin/python` instead of `uv run` | `uv run` re-resolves dependencies on every call | Intermittent failures | Documented in `CLAUDE.md` |

## 6. Performance and code-quality changes (Sept 2026 pass)

| Change | Why |
|---|---|
| `get_applicants_flat()` puts `LIMIT` into the SQL (as a bound parameter) instead of calling `pandas.head()` | Avoids fetching the whole joined table into memory |
| Index on `loan_applicants.created_at` | The applicants join sorts by this column on every call. It was applied to the live DB with `CREATE INDEX IF NOT EXISTS`, because `create_all()` does not add indexes to tables that already exist. |
| `/comparisons/*` caches CSVs in memory, keyed by file modification time | Avoids re-parsing the CSV on every request; the cache refreshes automatically when training or benchmarking rewrites the file |
| `max_tokens` 2000 to 1500 for advisory generation | Shorter responses and fewer rambling endings |
| `*.zip` in `.gitignore`; removed backup zips | Repo hygiene |

These are structural improvements. With the current demo-sized database there is no meaningful before/after timing to report, so the paper should describe them as design decisions rather than measured speedups.

## 7. Successes

- A working, end-to-end reference system (PostgreSQL + FastAPI + Streamlit) rather than an offline notebook study. The live endpoints (`/health`, `/applicants`, `/comparisons/*`, `/predictions/{code}/advisory`) were each verified to return 200.
- Tuned XGBoost reaches ROC-AUC 0.978 with better-calibrated probabilities (Brier 0.047), and the two model-selection methods now agree.
- A from-scratch logistic regression that competes with library implementations once tuned (ROC-AUC 0.952).
- Two measurable RAG improvements from one root-cause fix (chunk size): better relevance, better cross-method agreement, and lower dense latency.
- A rule-based fallback, so the system still produces a report when the LLM provider fails.
- Per-applicant LIME explanations, a PDF export of advisory reports, and a Findings page that shows the experiment results from the live CSVs.
- A reproducible paper-figure pipeline (`scripts/generate_paper_figures.py`, 7 figures as PDF and 300 dpi PNG).

## 8. Lessons learnt

1. **Silent failures are the most dangerous kind.** The two most important bugs (embedding truncation and sklearn tag resolution) produced no error message. Each was found only by comparing numbers and noticing something that did not make sense.
2. **Check benchmark results before interpreting them.** Part of the "sparse vs dense disagreement" was a pipeline defect. Find root causes before drawing research conclusions.
3. **Tuning can change the conclusion, not just the score.** The composite-vs-ROC-AUC disagreement disappeared once models were tuned. Comparisons between untuned models can mislead.
4. **Model-selection criteria reward different things.** ROC-AUC rewards ranking; Brier rewards calibration. For an advisory system that reports probabilities to applicants, calibration matters.
5. **External APIs and platforms change underneath a project.** HF's task routing, sklearn 1.6's tag system and the end of macOS Intel wheels all broke working code without any change to the project itself.
6. **Platform constraints are part of the methodology.** Import order, thread pinning and one-at-a-time encoding are needed to reproduce the results on this hardware.
7. **Localisation affects data validity.** Currency, thresholds and policy text must change together.

## 9. Limitations and open items

- **Experiment 3 not executed:** no human evaluator data, and no Kappa value.
- **Small retrieval benchmark:** 20 queries, 8 documents, no labelled relevance judgements. Similarity scores stand in for relevance.
- **No resampling:** SMOTE and undersampling were not tried. Imbalance was handled with class weights and the choice of metrics.
- **Four of the eight originally planned algorithms** (SVM, gradient boosting, LightGBM, CatBoost) were never implemented.
- **Single dataset;** how well the model generalises to other lenders' data is untested.
- **Hosted LLM dependency:** the main generation path depends on HuggingFace's inference providers.
- **LIME, not SHAP:** a trade-off forced by the platform. LIME explanations are sampling-based and can vary between runs.
- **Housekeeping before final results:** fix the broken `.venv`, align `RAG_CONFIG` with the real values, and commit the September changes (they are currently uncommitted).
